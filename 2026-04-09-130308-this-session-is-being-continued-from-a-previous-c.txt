  《ChatLab 智能协作特性设计文档》专家评审报告

  ▎ v1.1 | 2026-03-31 | 评审范围：全文（七章 + 附录）

  ---
  一、架构设计专家

  总体评价：架构清晰，但边界有若干歧义需要澄清。

  优点

  - 双层数据库架构（会话库 + 全局库）分层合理，读写职责清晰
  - 全局数据库进一步拆分为 3 个专用
  DB（collaboration、knowledge_graph、identity）是好决策，避免单体 DB 过大

  问题与建议

  [A1] 三库跨库外键不可实施

  文档中 global_task.owner_global_user_id 引用 global_user(global_user_id)，但
  global_task 在 collaboration.db，global_user 在 identity.db，SQLite
  不支持跨文件外键。

  ▎ 建议：将外键约束改为"应用层保证"，并在文档中明确注明"跨库关联由应用层维护，
  非数据库约束"。或将 global_user 合并到 collaboration.db，identity.db 
  仅存映射关系。

  [A2] 导入时异步提取使用 setImmediate 存在问题

  setImmediate(async () => { ... })

  在 Electron 主进程中，大批量 LLM 调用（几十条批次 × N
  批次）会阻塞事件循环，且错误无法向上传播。

  ▎ 建议：改用 Worker Thread 或现有的 Worker 架构（文档 4.1 中已提到 
  Worker），并提供进度反馈 IPC 事件。

  [A3] 知识图谱节点唯一约束太严格

  UNIQUE(type, name) -- 实体唯一约束

  同一个名称"小明"在不同领域可能指代不同人。

  ▎ 建议：唯一约束改为 (type, name, namespace)，namespace 可以是 global_user_id 
  或会话 ID 前缀，或通过 properties 字段区分。

  ---
  二、数据库专家

  总体评价：SQL 设计扎实，索引完整，但有几处性能隐患。

  优点

  - 所有关联表都建了覆盖性索引
  - 使用 TEXT DEFAULT '[]' 存 JSON 数组是对 SQLite 的合理折中

  问题与建议

  [D1] source_session_ids TEXT DEFAULT '[]' 无法高效查询

  knowledge_item.source_session_ids 是 JSON 字符串，无法通过 SQL WHERE
  条件过滤。

  ▎ 建议：增加关联表 knowledge_source(knowledge_id, session_id, message_id)，与 
  task_source 保持一致的设计风格。

  [D2] task_edit_history 缺少时间索引

  任务编辑历史查询通常按 task_id + edited_ts 排序，目前只有 FK 无索引。

  ▎ 建议：添加 CREATE INDEX idx_task_edit ON task_edit_history(task_id, 
  edited_ts DESC);

  [D3] graph_edge 唯一约束对多条同类关系不友好

  UNIQUE(source_node_id, target_node_id, type)

  同一对节点之间相同关系类型可能在不同时间段多次出现（如两人多次协作同一类型任务
  ）。

  ▎ 建议：保留唯一约束，但在 properties 字段中存储时间线列表，或用 
  occurrence_count + source_message_refs 
  表达多次出现，文档中需明确说明这个设计取舍。

  [D4] knowledge_vector.embedding BLOB 没有维度保证

  不同 embedding 模型输出维度不同（1536 vs 768 vs
  384），混存后无法直接向量相似查询。

  ▎ 建议：在 knowledge_vector 中添加 dimensions INTEGER 字段，并在查询时过滤 
  WHERE model = :model。

  ---
  三、AI/LLM 专家

  总体评价：Prompt 设计实用，但批量处理策略和质量控制需要补充。

  优点

  - 任务提取 Prompt 有明确的输出格式约束和 confidence 字段
  - 双层 Schema 的 Prompt 设计（固定优先，动态补充）策略正确

  问题与建议

  [L1] 批量处理没有上下文连贯性

  for (let i = 0; i < messages.length; i += batchSize) {
    const batch = messages.slice(i, i + batchSize)

  固定窗口 50 条可能把一个跨越两批次的任务讨论截断。

  ▎ 建议：改用滑动窗口（overlap 5-10 
  条），或在批次边界保留前几条消息作为上下文。文档应明确 batchSize=50 
  的选择依据。

  [L2] FAQ 生成没有质量过滤

  detectQAPatterns 的检测逻辑仅描述为注释，缺少质量门控：

  ▎ 建议：明确 QA 对的质量过滤规则，如：最短回答字数、排除系统消息/表情回复、时
  间间隔上限等，避免大量噪声 FAQ 进入知识库。

  [L3] 实体名称跨批次不一致风险

  同一个人在不同批次可能被 LLM 识别为"小明"和"明哥"，导致图谱中出现重复节点。

  ▎ 建议：在 extractGraphFromSession 的 Prompt 
  中加入当前已知实体列表（graph_node 中的 name），引导 LLM 
  使用一致命名；或在提取后做实体归一化（与身份识别联动）。

  [L4] 缺少 LLM 调用失败的降级策略

  文档中 catch (error) { console.error(...) }
  的错误处理过于简单，导入完成但提取失败的情况没有重试机制。

  ▎ 建议：在数据库中记录提取状态（extraction_status: 
  pending/running/done/failed），支持后续"重新扫描"功能触发失败记录的重试。

  ---
  四、产品/UX 专家

  总体评价：功能定位清晰，但核心用户流程有几处漏洞。

  优点

  - ASCII 线框图直观表达了 UI 结构
  - 任务卡片展示了 AI 置信度 + 溯源消息，透明度良好

  问题与建议

  [P1] "我是谁"问题未解决

  待办清单依赖于识别"当前用户就是某个全局身份"，但文档没有描述用户如何声明自己的
  身份。

  ▎ 建议：需要增加"个人身份配置"的 UX 
  流程：首次使用时，让用户从昵称列表中确认自己的全局身份，或通过 Settings 
  页配置"我的昵称"，这是 Todo Tab 正确工作的前提。

  [P2] 待确认身份匹配的通知机制缺失

  pending_identity_match 表存储了待确认项，但用户如何得知需要确认？

  ▎ 建议：增加"系统通知"或 Sidebar badge 设计，提示用户有 N 
  条身份待确认，避免长期积压导致待办归属错误。

  [P3] 知识图谱大数据量时的交互策略不足

  UI 线框图展示了完整图谱，但风险表中提到"节点过多"是已知风险。

  ▎ 建议：补充初始渲染策略——如默认只展示 Person + Task 
  核心节点，其他类型折叠；或从"当前选中节点"出发展开 N 跳邻居，而非全量加载。

  [P4] Focus Tab 自动识别策略描述不具体

  3.3 只说"AI分析用户频繁提及或参与讨论的话题"，没有给出触发条件和频率定义。

  ▎ 建议：明确：触发条件（导入后？定时？手动？）、"频繁"的阈值（出现 >N 次、跨 
  >M 个会话？）、自动关注 vs 手动关注的优先级。

  ---
  五、安全/隐私专家

  总体评价：文档未涉及隐私与权限，需补充。

  [S1] 全局数据库包含跨会话聚合数据，缺少访问控制设计

  ~/.chatlab/data/global/
  下的数据库文件无任何加密说明，与会话数据库一样暴露在文件系统中。

  ▎ 建议：明确全局库是否与会话库采用同样的加密策略（如 
  SQLCipher）；如果是本地单用户应用，至少说明"与现有会话库加密方式一致"。

  [S2] LLM API 调用存在数据外泄风险

  导入时将消息批量发给 LLM API 提取任务，但聊天内容可能高度敏感。

  ▎ 建议：在配置项（Section C）中添加 privacyMode: 
  boolean，说明哪些内容会被发送给外部 
  API，并提供用户知情同意机制（首次使用时提示）。

  [S3] pending_identity_match 表无过期清理

  ▎ 建议：添加 expires_ts 
  字段，或在配置中说明清理策略，避免长期积累大量过期待确认记录。

  ---
  六、可测试性专家

  [T1] 提取流程没有测试策略

  文档的"实现计划"（5.1）中 Phase 6 提到测试，但全文没有测试设计。

  ▎ 建议：补充一节"可测试性设计"：
  ▎ - LLM 调用抽象为可 mock 的接口
  ▎ - 提供 fixture 消息集用于单元测试任务提取/图谱提取
  ▎ - 
  身份匹配算法（calculateNameSimilarity）纯函数，容易单测，需明确测试覆盖要求

  [T2] 工作量估算过于乐观

  Phase 5（Graph Tab，双层Schema + 可视化 + 时间过滤）估算 5-7
  人日，但实际图谱可视化（WebGL/Canvas 渲染、布局算法）通常需要选型和大量调试。

  ▎ 建议：Phase 5 中明确图谱渲染库选型（如 D3.js、vis.js、Cytoscape.js、AntV 
  G6），选型不同工作量差异极大。
